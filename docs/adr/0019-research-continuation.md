# ADR0019 — продолжение исследования после сбоя

Дата: 16.11.2026. Точечный ремонт по запросу пользователя «чини» после разбора последовательного прохода первых трёх тем.

## Причина

Шесть новых результатов и один использованный исторический read не помещались в `externalSources.max(6)`. Каталог добавлял сервер, поэтому платная generate-repair не могла устранить нарушение. Прочитанные страницы оставались в ledger, но отсутствовали в клиентском контексте следующего запроса. Планировщик воспринимал «продолжай» как обычный разговор; генератор и оценщик не получали явного состояния доступности поиска. Неверная буквальная цитата оценщика могла обнулить уже обсуждённый критерий.

## Решение

- `RESEARCH_LIMITS.pages=6` ограничивает новые страницы одного поиска. Общий каталог новых и исторических оснований ограничен прежним размером серверного envelope, а не шестью элементами. Проверка каждого источника по ledger сохраняется.
- В той же session/project/module/generation сервер находит последнюю исследовательскую попытку. Если она закончилась failed/unknown, завершённые read возвращаются в контекст нового запроса без повторения платных действий. Позднее успешное исследование заменяет эту попытку. Сброс темы и другая сессия не получают её источники.
- Восстанавливаются только отсутствующие среди уже доверенных клиентских источников страницы. После их доставки дальнейшее «продолжай» может снова искать сведения; повторное восстановление не запирает беседу в answer.
- Сервер формирует `recoveredSourceRefs`, привязанные к переданным read того же этапа и поколения. Клиент принимает их через `applyMemoryPatch` как исторические чтения прерванного ответа, сохраняя исходные requestId/retrievedAt. Без этой отметки неизвестный read другого запроса по-прежнему отклоняется. Отметка не принимается из модельного JSON и сама не даёт доверия на сервере: полный snapshot обязан совпасть с ledger.
- `researchRuntime` передаёт планировщику, генератору и независимому оценщику серверную доступность поиска; оценщик дополнительно получает реальные операции. Отсутствие поиска в текущем ходе не означает отсутствия инструмента. Конкретные ложные заявления поступают в существующую единственную generate-repair.
- Для короткого утвердительного продолжения незавершённой исследовательской темы схема плана требует research и непустой безопасный query. При восстановленных чтениях сначала завершается уже оплаченная работа. Вопрос о состоянии, отрицание и отдельное поручение «без поиска» не включают этот принудительный маршрут.
- Если оценщик по-прежнему считает критерий covered, но пересказал цитату, можно повторно использовать прежнюю буквальную поддержку, которая всё ещё присутствует в текущем контексте. Явные missing/partial, исчезнувшая цитата, needsRefresh и требование пользовательского выбора не обходятся.
- Чтения записывают разрешённый код причины, HTTP-статус при наличии и безопасное пояснение. Полные сообщения исключений не попадают в журнал или ответ.

## Границы

Лимиты новых страниц, времени, платных попыток, размеров запроса/ответа и общего бюджета остаются прежними. Старый ошибочный запрос не переисполняется: его повтор возвращает сохранённую ошибку; продолжение получает новый requestId. Извлечённые источники не становятся новым чтением или доказательством коммерческого результата. Конечный список коротких продолжений и проверка цитат не являются универсальной смысловой проверкой.
