# Память разговора и локальный RAG

Решение 15.11.2026 по прямому уточнению пользователя: «в результатах будет контекст, который мы достаём из общения с человеком», «кратко», «чтобы факты из этого чата не забывались и читались». Презентацию убрать из этой панели. Попробовать простую базу знаний для MVP, если это не требует большой инфраструктуры.

## Два разных источника контекста

**Память проекта** — сказанное человеком, обсуждаемые предположения и открытые вопросы. Модель возвращает полную краткую память текущего этапа вместе с обычным ответом: отдельного платного вызова нет. `ModuleState.memory` сохраняется через существующие validation/Web Locks/localStorage/import/export. Следующий запрос несёт память активного чата и других этапов, включая разговоры без вручную сохранённого итога. Старые резервные копии не требуют миграции.

В памяти максимум 6 вводных, 3 гипотезы, 3 вопроса; каждый пункт до 200 символов. Вводная имеет короткую точную цитату пользователя (4–240 символов). Сервер отбрасывает вводные с цитатами, которых нет в пользовательских сообщениях, описании или предыдущей актуальной памяти. Это проверка наличия цитаты, а не доказательство правильности её интерпретации. Инструкция требует отдельные утверждения и обновления цитаты при исправлении значения. Все вводные остаются словами пользователя; AI не создаёт verified-факты. Уточнение — обычным сообщением в чате.

У каждого снимка есть время. Текущая поправка пользователя приоритетнее предыдущих данных; при противоречии воспоминаний инструкция отдаёт приоритет более позднему снимку. Редактирование раннего сообщения не затирает более поздний снимок, а помечает его `needsRefresh` до следующего ответа. Повторная генерация раннего ответа также не заменяет новую память. Неуспех запроса оставляет прошлую память. Сохранённый пользователем итог остаётся самостоятельным документом: не заменяется автоматически, используется для готовности этапа и презентации. Краткая память не гарантирует сохранение всех подробностей длинного ТЗ.

В запрос передаются снимки общим объёмом до 14 000 символов: активный этап первым, остальные по свежести. Локально всё остаётся. По-прежнему есть общий лимит HTTP 128 KiB; обычная отправка заранее проверяет размер, автоматического сжатия больших итогов нет.

**База знаний** — внутренние методические заметки CoFounder в `server/knowledge.ts`: проблема, аудитория, интервью, альтернативы, рынок, бизнес-модель, экономика, команда, дорожная карта и MVP. Это редакционные материалы прототипа на основе существующих методических правил приложения, не документы исходного продукта, рыночные исследования или независимая экспертиза.

Поиск сопоставляет нормализованные слова/префиксы запроса с заметками, учитывает ключевые слова и текущий этап, возвращает до 3 фрагментов; без достаточного совпадения — пустой набор. Найденные фрагменты действительно входят в prompt до генерации. Это минимальный lexical RAG, без embeddings и векторной БД. Он ограниченно понимает синонимы и короткие контекстные реплики. Версия, заголовок и точный фрагмент возвращаются сервером отдельно от JSON модели, затем сохраняются с ответом и показываются в «Посмотреть источники». Метаданные не означают, что модель использовала каждую заметку; они показывают, что ей было передано. Модель не может подделать этот список через свой structured output.

`estimateMaxCost` использует тот же prompt с retrieval и памятью, поэтому добавленные токены входят в бюджет. Поиск локален, отдельной оплаты за хранилище/embedding нет. Результат и источники попадают в тот же idempotency cache. Веб-поиск отсутствует; `searchEnabled:false` по старому контракту означает именно отсутствие веб-поиска.

## Перезапуск отдельного чата — 15.11.2026

Пользователь запросил start over для каждого этапа без удаления проекта. `restartChat` очищает сообщения, черновик, предложение, память, полный итог и числовой сценарий только выбранного модуля. Другие разговоры и профиль остаются; зависимые итоги получают `stale`, зависимая память — `needsRefresh`. Подтверждение в интерфейсе объясняет эту границу. Перезапуск не вызывает AI и не меняет серверный журнал запросов/расходов.

Необязательный `ModuleState.resetAt` хранит границу нового разговора и проходит обычные сохранение, reload и JSON-экспорт/импорт. Старые проекты совместимы. В новом чате сохраняются вводные предшествующих этапов по графу зависимостей. Прежняя память и итоги остальных этапов исключаются, чтобы отброшенная идея не вернулась из дальнейшего обсуждения. Их обновлённые после границы материалы снова могут использоваться; числовые сценарии без собственной даты после перезапуска передаются только для текущего этапа и его предпосылок. Общие сведения профиля сохраняются. `getStageWelcome`, память и сборка запроса используют одно правило отбора источников.

Текущий запрос отменяется локально. Проверка принадлежности активного запроса в `execute` и наличия исходного пользовательского сообщения в `applyAnswer` защищает новый чат от запоздавшего ответа или ошибки; старый callback не снимает ожидание с нового запроса. Перезапуск не обещает отменить уже выполненную сервером генерацию. Автоматическое сжатие полной истории и дополнительная проверка фактов остаются отдельным будущим развитием.

## Следующая ступень

При готовом небольшом наборе качественных документов семантический поиск можно подключить ориентировочно за 0,5–1 рабочий день, проверку релевантности и ответов — ещё за 1–3 дня. Это оценка для текущего MVP, не гарантия: подготовка/права/обновление материалов и изоляция пользовательских документов могут занять больше времени. Для большой базы понадобятся подбор контрольных вопросов, версии источников, фильтры по доступу и удаление документов.

Один из вариантов — [OpenAI File Search](https://developers.openai.com/api/docs/guides/tools-file-search), который выполняет семантический и лексический поиск по загруженным файлам. [Vector stores](https://developers.openai.com/api/docs/guides/retrieval) автоматически делят документы на фрагменты и индексируют embeddings. Это возможное продолжение, в текущей реализации эти сервисы не подключены. Новая платная инфраструктура потребует корректного учёта её расходов в существующем общем лимите.

В исследовании исходного продукта видны API истории, ходы по этапам и сохранённые артефакты; конкретная серверная RAG/векторная архитектура не установлена (`../research/10_technical_findings.md`, T02).
