# ADR0011 — Одно проверяемое исправление ответа

15.11.2026. Обычный ремонт после исторической сборки; её verdict не меняется.

Структурно/численно неверная генерация оплачивалась, но оставляла поручение без результата. Теперь штатный provider разрешает ровно один generate-repair после завершённой генерации с корректным usage, если schema/grounding/узкая проверка пустого обещания не прошла. Полный исходный ответ передаётся как недоверенные данные вместе с конкретным field/rule и исходным контекстом. Источники/claims не удаляются кодом ради прохождения. Новая генерация проходит те же guards. Сеть, отказ, незавершённость и неопределённый расход не запускают repair.

Общая резервация включает plan, bounded search, generate и repair до первого платного шага. Для JSON escape повторно вложенного raw учитывается6×256KiB и полный prompt, каталог чтений, schema и output. Подоперация generate-repair имеет отдельный id/inputHash/usage/charged и validation metadata. Все шаги используют прежний ledger; cap total$15. Неиспользованный резерв освобождается штатным завершением. Максимум output usage API учитывает обе генерации; лимит одной генерации сохранён.

SSE продолжает отдавать временный текст постепенно. Перед repair сервер отправляет text.reset и настоящий composing progress; клиент убирает прежний preview, затем показывает новую генерацию. Память/итог применяются только после complete. Черновик пользователя, исходный requestId и транспортный retry сохраняются. Повторный неверный ответ даёт502 с конкретным ограничением и доступным продолжением, без применения rejected patch. Это не успешный итог этапа.

Узкий guard замечает «ниже сравнение/таблица/список» без результата, но не является универсальной проверкой смысла или встроенным оценщиком R32. Качество исправленного ответа и отсутствие потерянного существенного содержания проверяет независимая живая приёмка. Количество claims не фиксируется искусственно: корректное разделение/устранение дублей и явное неизвестное могут изменить форму.

Проверки: generation-recovery, исходные grounding replays, HTTP streaming, client stream parser и browser repair/draft/reload. Живая приёмка записывается отдельно в .repair/2026-11-15, не в исторический failed/not_run.
