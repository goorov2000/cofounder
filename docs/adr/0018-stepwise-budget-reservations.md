# Поэтапный резерв AI-бюджета — 16.11.2026

## Причина

Пользователь показал отказ BUDGET_EXHAUSTED и поручил исправить расчёт без повышения общего потолка. При лимите $15 журнал учитывал $4.642941473; последний успешный ход резервировал $10.328788, а стоил $0.09261. Общий резерв заранее складывал план, исправление плана, дополнительные методики, поиск, обе генерации с максимальными страницами и максимально испорченным ответом, затем оценщика. Рост контекста блокировал обычный диалог при существенном остатке.

## Решение

Обычный HTTP-запрос резервирует первый шаг через `estimateInitialCost`, сохраняя прежние ограничения владельца, requestId, хеша, частоты и параллельности. Серверный `Reservation.stepwise` включает поэтапный учёт; клиент его задать не может. Схема SQLite и старые записи совместимы без миграции или пересчёта прошлого расхода. Старый режим полного резерва сохранён для существующих прямых пользователей ledger.

Перед каждым платным вызовом `recordOperation(started)` в одной BEGIN IMMEDIATE-транзакции проверяет сумму остальных запросов, уже учтённых дочерних шагов и нового резерва. Только после успешной записи вызывается транспорт. Завершённый шаг заменяет свой резерв известной стоимостью; неопределённый продолжает занимать весь свой резерв. Сумма хранится в родительской записи: перезапуск и истечение pending сохраняют завершённый расход и резерв реально начатых шагов.

Стоимость шага ограничивается полным сериализованным запросом в UTF-8, включая схему, инструкции, реально загруженные методики/страницы и фактически экранированный rejectedOutput, плюс 16384 на оформление. Один байт на входной токен остаётся консервативной границей; деления на среднее число символов в токене нет. Выход, тарифы длинного контекста, максимальный вход Sol и отсутствие скидки кеша сохранены. Только поиск дополнительно резервирует прежние четыре окна 128000 и три платных действия. Usage сверх денежной границы шага отклоняется с сохранением его неопределённого резерва, без повторной оплаты.

`estimateMaxCost` по-прежнему даёт полный консервативный предел независимому `AppOptions.admit` и планировщикам проверок с отдельными ограничениями расхода. В обычном HTTP-пути он не блокирует диалог и не вычисляется без такого callback.

## Последствия

Последующий шаг может не поместиться, хотя предыдущий уже оплачен. В таком случае он не начинается, прежний расход сохраняется, а повтор того же запроса возвращает сохранённый исход. Готовый ответ остаётся доступным, если бюджета не хватило только оценщику; оценка помечается unavailable, готовность темы не подделывается. Сохранённые проекты, черновики и экспорт доступны при отказе. Сообщение показывает доступный остаток и нужный резерв; клиент не добавляет старое указание обязательно повышать лимит.

Общий разрешённый потолок $15, DATA_DIR, ключ, модели и прошлый журнал не меняются. Уточнение заменяет предварительный полный денежный резерв из ADR0005/0007/0011/0012 по прямому поручению пользователя; предельное количество шагов, времени, поиска и выходных токенов остаётся прежним.
